# 補完候補コーパスの作り方

[English](../corpus.md) · [照合仕様](matching.md)

## 既定の入力元

確定後にホストが検索する文書とフィールドから、日本語の補完語を生成します。文書スナップショットのIDと、`{"id":"doc-1","text":"りんごを食べた。"}` のようなUTF-8のJSONLを使います。質問文が検索対象なら質問文を、タイトルと本文が検索対象なら両方を決めた順序で同じ文書IDにまとめます。表示用の抜粋など、検索範囲外のフィールドは除外します。入力文書のIDは一意にします。

ネイティブCLIで [SudachiのRust実装](https://github.com/WorksApplications/sudachi.rs) を使い、固定済みの辞書スナップショットとバージョン付きの抽出設定を指定します。Sudachiの品詞 `名詞`、`動詞`、`形容詞` と分割モードBから始めます。空のキーを拒否し、設定可能なストップワード・除外品詞の規則を適用します。M1で標本を記録し、分割モード、未知語、頻出でも補完に適さない語、不要な固有名詞を確認してから既定の設定を確定します。

## 抽出、集計、索引生成

1. 名詞はSudachiの正規化形、動詞と形容詞は辞書形に正規化した見出し語を採用します。正規化済みの表示キーでまとめます。表示形が複数あればUTF-8のバイト順で最初のものを残します。単語を1文字ずつに分割せず、語として保持します。例えば `食べた` は表示候補 `食べる` に対応付けられます。
2. 同じ語は文書ごとに最大1回数えます。既定の `weight` には、その語が出現した文書の数を使います。同じ記事内に何度出ても重みは増えません。確認済みの適切な表記の揺れを別名として保持し、辞書の読みとローマ字も候補ごとの上限内で加えます。別名の出現頻度は順位に影響させません。読みが同じでも異なる語は分けて保持します。
3. 決定的な候補JSONLを出力します。抽出した候補はUTF-8の正規化キーで並べ、数値IDを1から割り当てます。候補集合が同じならIDは安定し、有効範囲はその索引世代です。外部の作成側は候補を直接入力する際に独自の安定したIDを指定できます。文書スナップショット、正規化した入力と出力のハッシュ、辞書と設定の識別情報、候補数、別名数、除外理由ごとの件数を記録します。
4. 候補JSONLをビルダーに渡します。ビルダーは手作業で選んだ候補や他言語の候補も同じ形式で扱い、コンパクトな読み取り専用索引を生成します。入力行長、形態素解析の入力長、一意な文書数・語数、別名数に上限を設けます。上限を超えるとジョブは失敗し、公開済みの世代は引き続き利用できます。検証を通過した世代を一単位で公開します。

## 出現頻度と順位のメタデータ

ビルド時に、候補IDをキーにした別のJSONLを出力します。`df`（その語が現れた文書数）、`cf`（対象トークンの総出現回数）、実験用の `bm25_sum` 重みを格納します。集計対象は正規の語だけです。例えば同じ語が文書Aに2回、文書Bに1回出れば、`df = 2`、`cf = 3` です。順位付け方式、パラメータ、文書統計は来歴に記録します。既定値は `weight = df` です。ブラウザは、一致品質と変種・キーの優先度が同じ場合に限り、選択した整数の重みを使います。

通常のBM25はクエリに対して文書を採点します。この実験では候補語 `t` を1語のクエリと見なし、その語を含む文書 `d` ごとに採点して、ビルド時に文書全体で合計します。`tf` は `d` 内での `t` の出現回数、`N` は入力文書数、`dl` は `d` 内の重複排除前の対象トークン出現数、`avgdl` は全入力文書における `dl` の平均です。初期値を `k1 = 1.2`、`b = 0.75` とし、次の正のIDFを使います。

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
bm25(t, d) = idf(t) * tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl))
bm25_sum(t) = sum of bm25(t, d) for documents that contain t
```

文書ごとの語の件数を使い、上限付きの2パス処理を決まった順序で行います。空コーパスでは採点する語はありません。候補語があれば、そのコーパスの `avgdl` は必ず正です。実験では `bm25_sum × 1,000` を四捨五入し、オーバーフローと非有限値を拒否します。記録したツールチェーンで再現性を確認します。この整数を順位の重みに設定できます。統計JSONLはビルド成果物として保持し、配信用の索引には選んだ重みだけを含めます。IDFは希少性を評価しますが、文書内で目立つ語が補完でも適切とは限らないため、`df` と比較します。[RobertsonとZaragozaによるBM25の論文](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf) · [LuceneのBM25Similarityと正のIDF](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html)。

## CLIとデモの準備

M3で実装するコマンド案です。

```sh
nemesia extract --input documents.jsonl --dictionary system.dic --policy corpus-policy.json --output candidates.jsonl --stats term-stats.jsonl
nemesia build --input candidates.jsonl --output suggestions.nmsi
```

CLIのコマンドと、入力解析、形態素抽出、変換ルール、来歴記録は本体リポジトリが担当します。デモは小さな準備スクリプトを持ち、実際の検索対象フィールドを文書JSONLに出力し、固定したCLIを呼び出して期待するハッシュを検証します。この構成なら、後段の検索サービスを問わず抽出処理を使えます。

CIでは、独自に作成した決定的な小規模コーパスを使います。デモの後段の検索が同じ質問文を対象とする場合、大規模ベンチマークには、固定した [AutoWikiQA](https://huggingface.co/datasets/cl-nagoya/auto-wiki-qa) の質問文の一部を入力文書として使えます。配布前にデータセットのリビジョン、抽出結果、出典表記を固定し、適用されるデータライセンスを保持します。入力文書数、一意な補完語数、別名キー数は分けて計測します。文書が1万件あっても、補完候補が1万件とは限りません。
