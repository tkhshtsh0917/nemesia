# 照合仕様

[English](../matching.md) · [アーキテクチャ](architecture.md) · [ロードマップ](roadmap.md)

v0.1の照合仕様です。全件走査の参照実装で最適化の比較対象となる期待結果を固定します。

## 候補と正規化

CLIはUTF-8のJSONLを受け取ります。各行に安定した `u32` の `id`、選択時に返す空でない `text`、任意の `u32` の `weight`（既定値は `0`）、任意の文字列配列 `aliases` を含めます。1行が1件の補完候補に対応します。候補IDは一意にします。同じ表示文字列が複数あればビルドエラーとし、どのIDと重みを残すかはデータ作成側が決めます。表示文字列が異なる候補で照合キーが一致することは許可します。1行内で正規化後のキーが重複する場合は、優先度が最も高いものを一つ保存します。

```json
{
  "id": 42,
  "text": "ビートルズ メンバー",
  "weight": 20,
  "aliases": ["beatles members", "びーとるず メンバー", "bi-toruzu menba-"]
}
```

照合キーとクエリは、同じRust実装と固定したUnicodeデータで正規化します。NFKC、Unicodeスカラー値ごとの小文字化の順に適用し、連続するUnicode空白を1個のASCIIスペースにまとめます。先頭の空白は取り除きます。索引キーの末尾空白は取り除き、空でないクエリの末尾にはスペースを1個残します。距離は正規化後のUnicodeスカラー値で数えます。表示と選択には元の表示文字列を使います。

正規キーは表示文字列を正規化したものです。それ以外のキーには、明示的に与えた別名やビルド時に作るフレーズ全体の読みを使います。フレーズ全体の読みでは、先頭の語を含めて語順を保ちます。v0.1の自動別名生成では、単独の同義語、先頭語を削った表現、部分文字列を対象外にします。別のフレーズを候補につなげる場合は、データ作成側が別名として明示できます。

## 一致条件と順位

正規化した空でないクエリ `q` とキー `s` に対して、`q` から `s` の空でない各接頭辞へのLevenshtein距離の最小値を求めます。挿入・削除・置換をそれぞれコスト1で数えます。選ばれた接頭辞より後ろの文字にはコストがかかりません。隣接する異なる2文字の交換は通常の編集操作として評価します。空入力と空白だけの入力には候補を返しません。

各クエリ変種の正規化後の長さが1〜2スカラーなら編集上限は `0`、3〜5なら `1`、6以上なら `2` を既定値とします。末尾に正規化されたスペースがある変種の上限は、語境界を保つため `0` とします。以上をv0.1の既定値とします。

| 入力                     | キー               | 期待結果                          |
| ------------------------ | ------------------ | --------------------------------- |
| `bi`                     | `bi-toruzu menba-` | 距離0                             |
| `bi`                     | `possibility`      | 対象外                            |
| `toky st`                | `tokyo station`    | 距離1                             |
| `new `（末尾にスペース） | `newark`           | 対象外                            |
| `new `（末尾にスペース） | `new york`         | 距離0                             |
| `びーt`                  | `bi-toruzu menba-` | 変換後の `bi-t` を使う場合、距離0 |

一致した経路はまず距離で比べ、同点なら変換したクエリより原入力を、次に別名より正規キーを優先します。候補IDごとに、全キーと両方のクエリ変種のうち最良の経路を採用します。候補はその評価順で並べ、同点なら重みの降順、さらに同点ならIDの昇順とします。一致し得る経路を比較し終えるか、省略しても上位 `k` 件に影響しないことが確認できてから、`k` 件を返します。別名によって同じ候補を追加したり、重みを加算したりすることはありません。実行時は一貫してIDで候補を識別します。

CLI、ネイティブRust、WASMはいずれも同じリクエストで原入力と任意の変種1件を受け取ります。ブラウザは上限付きの変換表を使い、かなと英字の混在入力から異なる変種を1件作れます。変換できる場合は原入力が一致していても両方を送ります。エンジンは同じ索引世代で両方の入力を正規化し、まとめて順位付けします。

## 正しさの参照実装

テストでは全件走査で関連する空でない接頭辞を列挙し、スカラー値単位のLevenshtein DPで比較します。その後、独立に全件ソートして重複を除きます。順序付きのID、距離、同点時の順位を比較し、後から評価した別名が候補の評価を改善するケースも含めます。上記の例、日本語、正規化による衝突、補助平面の文字、結合文字、入力が候補全文と一致する場合、1文字入力、複数候補で共有するキー、重みが大きい曖昧一致、エラー後の有効な入力を網羅します。少数の文字種を使った全列挙とシード固定のランダムなコーパスでも、最適化した索引を照合します。

接頭辞距離は既存の曖昧接頭辞一致の定義に従います。上記の編集方針、クエリ変種、順位はNemesiaで決めるものです。[Vespaの曖昧接頭辞一致の説明](https://docs.vespa.ai/en/querying/text-matching.html#fuzzy-prefix-match) · [BastとCelikikによる論文](https://ad-publications.cs.uni-freiburg.de/TOIS_fuzzy_BC_2013.pdf)。
