## リポジトリと実行の境界

| 担当                                                         | 責務                                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `nemesia-index`                                              | バージョン付きのバイナリ配置、検証付きの読み取り、共通データ型と共通のテキスト正規化    |
| `nemesia-engine`                                             | クエリの準備、接頭辞照合、順位、クエリの資源上限                                        |
| `nemesia-builder`                                            | 候補JSONLから決定的に索引を生成                                                         |
| `nemesia-analyzer`                                           | 辞書と設定を明示した、日本語候補と読みのネイティブ専用抽出                              |
| `nemesia-cli`                                                | ネイティブの `extract`、`build`、`inspect`、`suggest` コマンド                          |
| `nemesia-wasm`                                               | 同じ索引バイト列を扱う、同じエンジンの読み取り・照合用の薄い境界                        |
| [nemesia-demo](https://github.com/tkhshtsh0917/nemesia-demo) | TypeScriptアダプター、デモ用データ、アクセシブルなコンボボックス、ブラウザテスト、Pages |

ビルドジョブは、後段の検索サービスが使う文書スナップショットから同じ検索対象フィールドを取り出し、抽出と索引生成を実行します。WebサービスやCDNがハッシュ付きの成果物を配信します。ブラウザではWorkerが索引を読み込み、WASMに補完を要求します。ページは候補文字列を表示し、選択や送信時に確定したクエリをホストの検索に渡します。スタンドアロンのデモでは、検索バックエンドを呼ばずに確定クエリを表示できます。

WASMの依存関係は読み取り、エンジン、共通の正規化、呼び出し境界で構成します。トークナイザー、辞書、コーパスの取り込み、書き込みはビルド時だけ実行します。ホストが送信するまでは、ブラウザは入力や補完候補をリモートサービスに送りません。v0.1は不変の完全スナップショットを使い、ベクトル検索、クエリログ収集、差分更新プロトコルは対象外です。

## 索引、配信、呼び出し境界

v1はリトルエンディアン形式です。拡張子は `.nmsi`、マジック値は `NMSI` です。ヘッダーに形式バージョン、ファイル長、正規化の改訂番号、セクションディレクトリを格納します。各セクションは固定幅の候補レコード、キーから候補への参照、探索構造、UTF-8文字列を持ちます。探索構造は固定幅のTrieです。[バイト配置](format.md)に詳述します。オフセットと件数には検査付き算術を使い、未知の必須機能、重複するセクション、不正な長さ・UTF-8・ID・参照・探索順序は使用前に拒否します。WASM ABIと索引形式は独立してバージョン管理します。

データマニフェストは、形式と正規化の改訂番号、世代、任意のクエリ変換表を含む各成果物のバイト長とSHA-256を関連付けます。候補入力のハッシュを記録し、抽出コーパスでは辞書と設定の識別情報も記録します。不変のファイルは世代ごとのURLで提供します。新世代をバイト上限内で読み込み、内容を検証し、索引と変換表を検査してから同時に切り替えます。読み込みに失敗しても現行世代を使えます。原子的な切り替えでは一時的に2世代を保持できるため、ローダーは切り替え前に合計メモリを検査します。2世代を保持できない場合、アプリは明示的に再読み込みします。ハッシュは成果物の取り違えを検出します。マニフェストと更新ポインターは信頼する配信元から取得します。文書由来の補完索引をCDN配信する際は、元の文書群と同じ閲覧範囲に限定します。

呼び出し境界は内部を隠した索引ハンドル、原入力・任意の変種1件・`limit` を含む上限付きリクエスト、順序付きのID・表示文字列・編集距離を含む所有権付き結果を公開します。明示的な破棄を用意し、未対応の入力、検証失敗、資源上限超過には型付きの回復可能なエラーを返します。後続の検索や索引の破棄後も取得済みの結果は有効です。TypeScriptラッパーはWASMに文字列を渡す前に不正なUTF-16を拒否します。クエリの失敗後も索引は再利用できます。

| 初期上限                       | v0.1の提案値                                                                                                               |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 件数                           | 既定8、最大20                                                                                                              |
| 正規化前後それぞれのクエリ変種 | 最大128 Unicodeスカラー、512 UTF-8バイト。全体で最大2変種                                                                  |
| ビルド入力                     | キーおよび表示文字列ごとに正規化後は最大256スカラーかつ1,024 UTF-8バイト、正規化前も1,024バイト。候補ごとに別名キー最大8件 |
| 索引と変換表                   | 展開後の索引は最大32 MiB、クエリ変換表は最大2 MiB、最大20万候補                                                            |
| 実行時の処理量                 | 両変種で一つの総処理量上限を共有し、訪問ノード、検査した投稿、帯状DPセルなどに課金し、上限は1,200万単位                    |
| メモリ                         | アプリが所有する索引と検索状態のピークを世代ごとに64 MiBとする目標。ローダーは世代が重なる準備中の量を別に計測し制限       |

可能な限り、割り当て・展開前に上限を適用します。展開後のバイト数と観測したメモリを転送サイズと分けて検証します。処理量の上限内に完了できなければ、未完了と区別できない上位候補を返さず、型付きエラーにします。ネイティブCLI、生のWASM、ABIメタデータ、対応するwasm-bindgenのツールチェーン識別情報、チェックサム、ライセンス表記をタグのRelease Assetsにまとめます。デモは固定済みリリースからバインディングを生成し、検証します。ブラウザコードと依存ロックファイルはデモに置きます。小さな共通コーパスでネイティブ、CLI、WASMの出力が一致することを受け入れ条件とします。
