## Algorithm choices and benchmark plan

The initial fuzzy path uses trie traversal with a banded Levenshtein row and the best accepted distance on its ancestor path. A prefix that has already accepted may still produce valid descendants. Pruning for edit distance requires that the best accepted ancestor and the lower bound for future accepted prefixes both exceed the budget. Explore rank bounds only when the tie breaks and alias deduplication are accounted for. Compare FST/trie compression, prefix-state reuse across keystrokes, or prefix-specific Bitap after M2. Each optimized implementation must match the oracle first. See [fuzzy prefix search research](https://ad-publications.cs.uni-freiburg.de/TOIS_fuzzy_BC_2013.pdf) and the [Rust fst Levenshtein documentation](https://docs.rs/fst/latest/fst/automaton/struct.Levenshtein.html).

Use 10k and 100k distinct candidates, with candidate, key and document counts recorded separately. Add a common-prefix stress corpus, no matches, long input, Unicode, mixed IME, repeated variants and rapidly replaced input. An exploratory 1M-candidate run may guide later work. Measure extraction and index build time, peak native memory, raw and compressed assets, transfer through worker readiness, warmed WASM time, Worker round trip and input to accepted DOM update separately. Use exact/fuzzy latency histograms (p50/p95/p99, sample count and budget failures) and replay seeded traces on Chromium, Firefox and WebKit. Emulated mobile profiles cover layout and behavior. Label lab timings with the actual host.

Initial targets for 100k candidates on a recorded desktop reference host, with assets loaded, are p95 ≤ 10 ms for exact and fuzzy WASM calls reported separately and p95 ≤ 50 ms from input to accepted DOM mutation for the representative typing trace. Record budget exits and misses independently and require zero budget exits on that trace. Keep the index and runtime within the proposed resource limits. Stress cases must agree with the oracle or fail with the documented budget error. These are release targets subject to M6 measurements.

Evaluate quality with held-out prefixes and typos tagged with intended candidates. Compare document frequency with the offline BM25 weight using Recall@8, MRR@8 and top-1 accuracy on clean, typo and Japanese reading subsets. Inspect high-frequency distractors and noisy rare terms. Record dataset, dictionary, policy, seed, toolchain, hardware and artifact identities. Repeat paired performance runs against an unchanged baseline. Keep failure cases and full conditions reproducible, and move performance figures into public documentation only after they're measured.
